# Releasing

Preview `0.3.0-rc.2` was published on 2026-11-21 at 08:10:15 UTC from tag `v0.3.0-rc.2`, commit `94ca704dddcbcd5bdb7003d8fd604127d6482674`. See the [release workflow](https://github.com/nilzx/dsh-mcp-connector/actions/runs/44883471824) and [GitHub prerelease](https://github.com/nilzx/dsh-mcp-connector/releases/tag/v0.3.0-rc.2). The existing npm package's trusted publisher must authorize this repository and `.github/workflows/publish.yml` for direct publishing. GitHub-hosted runners use OIDC; no long-lived publish token is required. Confirm the npm trusted publisher configuration before any release. See [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/).

The workflow has two jobs. The package job has read-only repository permission, validates strict SemVer and event routing, runs the full suite with isolated dsh 0.2.2-rc.5 and esbuild 0.28.2 on Node 24 with zero skipped tests, packs once, installs that exact tarball in isolation, checks its materials and uploads it with a digest. Pull requests and a manual `workflow_dispatch`, even against a tag, stop there. The package `publishConfig.tag` must match the route (`next` for a prerelease, `latest` for stable) before any event proceeds. A push of an exact `v<package.json version>` tag can start the publish job after the package job succeeds. The publish job verifies the digest and publishes that same tarball via OIDC; it does not repack. Prereleases go to npm `next` and a GitHub prerelease; stable versions go to npm `latest` and a normal GitHub release. The candidate's `publishConfig.tag` is also `next` for source-directory publication; npm 11 tarball publication still requires an explicit --tag; a future stable version must update that default and pass --tag latest.

Review version, lockfile, compatibility and [migration/rollback](PREVIEW.md) before tagging. Tags and npm versions are immutable: an incorrect published version requires a new version, not an overwrite. Publish, deployment and changes to existing instances are separate actions. If npm succeeds but GitHub release creation fails, inspect registry and release state before any retry; do not blindly republish.

The checks do not certify the host or server. The manual workflow tests package contents and installation; the installed real host module checks do not validate every executor or establish full host/server interoperability; use the separate configured acceptance checks. Each future release still requires verification of its own GitHub Actions and npm OIDC result.

The earlier connector `v0.3.0-rc.1` tag's workflow failed before npm upload because the tarball path lacked `./`; no connector rc.1 package was uploaded by that run. That failed tag remains unchanged; rc.2 is the corrected preview. The package job performs an unauthenticated npm 11 dry run on the same tarball before upload.

Post-publication verification downloaded the registry tarball in an isolated Node 26.13.1 environment, checked its SHA-512 and byte equality with the release workflow artifact, installed it, imported the package and verified the three bundled admission materials. At that check, `next` was `0.3.0-rc.2` and `latest` was `0.2.2`. This is package verification, not certification of a host or server.
