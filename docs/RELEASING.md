# Releasing

The candidate version is `0.3.0-rc.1`. No publication is implied by this document. The existing npm package's trusted publisher must authorize this repository and `.github/workflows/publish.yml` for direct publishing. GitHub-hosted runners use OIDC; no long-lived publish token is required. Confirm the npm trusted publisher configuration before any release. See [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/).

The workflow has two jobs. The package job has read-only repository permission, validates strict SemVer and event routing, runs the full suite with isolated dsh 0.2.2-rc.5 and esbuild 0.28.2 on Node 24 with zero skipped tests, packs once, installs that exact tarball in isolation, checks its materials and uploads it with a digest. Pull requests and a manual `workflow_dispatch`, even against a tag, stop there. The package `publishConfig.tag` must match the route (`next` for a prerelease, `latest` for stable) before any event proceeds. A push of an exact `v<package.json version>` tag can start the publish job after the package job succeeds. The publish job verifies the digest and publishes that same tarball via OIDC; it does not repack. Prereleases go to npm `next` and a GitHub prerelease; stable versions go to npm `latest` and a normal GitHub release. The candidate's `publishConfig.tag` is also `next` as a defense against an accidental manual publish; a future stable version must review that default.

Review version, lockfile, compatibility and [migration/rollback](PREVIEW.md) before tagging. Tags and npm versions are immutable: an incorrect published version requires a new version, not an overwrite. Publish, deployment and changes to existing instances are separate actions. If npm succeeds but GitHub release creation fails, inspect registry and release state before any retry; do not blindly republish.

The checks do not certify the host or server. The manual workflow tests package contents and installation; the installed real host module checks do not validate every executor or establish full host/server interoperability; use the separate configured acceptance checks. GitHub Actions and npm OIDC publishing must be verified in the actual repository when a release is explicitly authorized.
