# Preview migration and rollback

`0.3.0-rc.2` is a published preview, not a claim of production readiness. It was released from tag `v0.3.0-rc.2` at commit `94ca704dddcbcd5bdb7003d8fd604127d6482674` on 2026-11-21. See the [workflow](https://github.com/nilzx/dsh-mcp-connector/actions/runs/44883471824) and [GitHub prerelease](https://github.com/nilzx/dsh-mcp-connector/releases/tag/v0.3.0-rc.2). The earlier `v0.3.0-rc.1` tag remains as a failed pre-upload attempt. Install the exact version or the `next` dist-tag deliberately; at post-publication verification `next` was rc.2 and `latest` was 0.2.2. The downloaded tarball matched the workflow artifact byte for byte and passed isolated installation and import checks; this does not certify a host or server. Node >=20 is declared by the connector. dsh 0.2.2-rc.5 declares Node >=24.9.0. Release host validation uses Node 24 with the reviewed dsh sources and esbuild 0.28.2. Earlier Node 22.23.5 checks exercised only selected host modules and the isolated builder; they do not establish support for the full dsh application on Node 22.

Ordinary MCP configuration remains compatible without a capability profile. `turn-sync` and `trusted-lifecycle` are opt-in connector/host requirements, not MCP standards or certifications. Stock dsh 0.2.2-rc.5 lacks the synchronous creation admission required by `trusted-lifecycle`; the [optional reviewed host proposal](../contrib/dsh-session-admission/README.md) is not automatically installed. Validate the intended host, scoped executor and server together before relying on a profile.

Before upgrading, stop affected conversations and back up the profile, session logs, and all connector durable sidecars together. Preserve ownership, history references, delivery markers and cursors. Record exact package and host versions, configuration, and backup location. Test the candidate in an isolated profile first. A missing service, changed endpoint, lost sidecar, unsupported executor or failed refresh must block the affected work; do not disable the controller or delete state to bypass a failure.

For rollback, stop affected conversations, restore a consistent backup of the previous package, host modules, configuration, session logs and matching sidecars, and verify the previous version in an isolated profile before resuming. A package-only downgrade may not understand newer state or restore the same guarantees; do not mix mismatched snapshots. Resolve uncertain recovery with the documented service-specific authorization rather than inventing parent metadata or resetting cursors. npm dist-tag changes and deployment are separate operator actions.
